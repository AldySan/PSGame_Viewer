# Contributing to PSGame-Viewer

Thanks for wanting to help! This guide covers everything from reporting a broken file to getting a pull request merged. No prior contribution experience is needed — if you get stuck anywhere, open an issue and ask.

## Ways to help

- **Report a file that won't open.** Parser coverage is the heart of the project. A clear report with the error message and a synthetic (or otherwise legal-to-share) sample goes a long way.
- **Report crashes or odd behavior**, including anything that looks wrong in the UI.
- **Suggest a feature.** Small, focused ideas fit best — this is a viewer, not an extractor or a manager.
- **Improve a translation.** The strings live in `i18n/*.ts`; even one corrected sentence helps.
- **Write code.** The good-first-issue kind of work is usually a new format variant, a missing details row, or a test.

## Setting up the project

You need CMake 3.21+, a C++17 compiler, Qt 6.5+ (Core, Gui, Quick, Quick Controls 2, Network, Sql, Xml) and zlib. The [README](README.md#getting-started) has the details, including what to do when your distribution's Qt is too old.

```sh
git clone https://github.com/AldySan/PSGame_Viewer.git
cd PSGame_Viewer
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure   # 30 tests, takes seconds
```

The tests run against synthetic fixtures generated by `tests/fixtures/generate.py` — no copyrighted files needed, ever. If you touch a parser, update the generator and regenerate them:

```sh
python3 tests/fixtures/generate.py   # writes the fixtures next to itself
```

For quick manual checks without a display:

```sh
QT_QPA_PLATFORM=offscreen \
PSGV_OPEN=tests/fixtures/ps4_cnt.pkg \
PSGV_SCREENSHOT=/tmp/shot.png \
./build/psgame-viewer
```

The update checker can be pointed at a fixed JSON response for testing:

```sh
PSGV_UPDATE_API=file:///path/to/release.json ./build/psgame-viewer
```

## How the code is organized

```
src/core/     parsing library, no UI code — one module per platform
src/app/      controllers and models between QML and the core
src/qml/      the Qt Quick interface
tests/        unit tests + the fixture generator
```

The split matters: `src/core` is the parsing library — it may only use Qt Core, Xml and Sql, and nothing in it may include QML or widgets. If your change touches a file format, it belongs in `src/core`; if it touches what the user sees, it's `src/qml` or `src/app`.

## Code style

The project follows consistent conventions — matching them matters more than personal preference:

- C++17, `camelCase` for functions and variables, `PascalCase` for types, `m_` prefix for members
- Qt idioms throughout: `QStringLiteral` for literals, `QLatin1String` in comparisons, `u'x'` for character literals
- Braces on their own line (Allman), 4-space indent, no tabs
- Comments explain *why*, in the same plain tone as the rest of the file
- QML: one component per file, `qsTr()` around every user-visible string

When in doubt, open the file you're editing and copy what's already there.

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/) — `type: short summary`, optionally `type(scope): summary`, with a body when the reason isn't obvious from the title:

```
fix(core): reject TRP entries whose offset+size wraps

A crafted entry could pass the bounds check by wrapping the u64 sum.
The check now tests offset and size separately.
```

Common types: `feat`, `fix`, `docs`, `test`, `chore`, `refactor`.

## The pull request flow

1. **Start from `dev`.** All development merges into `dev`; `main` tracks the stable state.
2. **Create a branch** with a short, descriptive name: `feature/ps3-trophy-parsing`, `fix/exfat-readonly-crash`, `docs/faq`.
3. **Keep it focused.** One logical change per PR. A format fix and a theme redesign belong in two PRs.
4. **Add a test** when it makes sense — a new parser path should always get one, and `tests/tst_psgcore.cpp` has plenty of small examples to copy from.
5. **Run the checks** before pushing: build, `ctest`, and a quick manual look at the UI if you touched QML.
6. **Open the PR against `dev`** and fill in the template. Screenshots of before/after help a lot for UI changes.

CI builds and tests every PR on Linux with Qt 6.8. It has to pass before a merge — if it fails for reasons that look unrelated to your change, say so in the PR and it will get sorted out.

## Adding a new file format (a practical example)

This comes up often enough to deserve its own short walk-through:

1. Add the parser under `src/core/<platform>/`, register the extension in `src/core/detect.cpp`, and wire it into `CMakeLists.txt`.
2. Add a builder for a synthetic fixture in `tests/fixtures/generate.py` and a test in `tests/tst_psgcore.cpp`.
3. Check the details rows: the spec card should make sense for the platform (see `src/core/details.cpp`).
4. If the format can carry covers or trophies, the generic gallery/trophy code picks them up from the entry list — look at how the existing formats do it.
